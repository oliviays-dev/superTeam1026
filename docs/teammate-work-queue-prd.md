## 1. 背景与问题

AI Teammate 已能承接任务、执行会话并产出结果，但围绕「这个分身有哪些活、按什么顺序干、干完交给谁」缺少完整闭环。近期评审暴露三个问题：

1. **工作计划与任务管理的数据对不上。**
   工作计划页展示「指派给该实例、状态待处理」的任务，任务管理看板按「责任人」筛选；当责任人仍是老形态的员工身份 id、或用户按同名实例筛选时，两边结果不一致。
2. **执行有记录，但没有回到任务。**
   Agent 跑完并有输出反馈，任务却没有「回到人类手上」：状态虽会转「待验收」，责任人仍是 Agent，实例 owner 既看不到「待我确认」，也不会进他的工作台待办。
3. **人不在岗时缺少前置准备。**
   下班后要让队列继续跑，但所需工具、资源范围没有提前对齐；夜里缺权限只能空跑，第二天才发现。

> 定位说明：**产品本体是「给 Teammate 的待办任务列表 / 工作计划项」**，也就是本文档的「任务队列」。所谓「夜班」只是「人类不在岗时段让队列自动有序执行」的一个使用场景，不引入独立的业务对象。

## 2. 目标

1. **一套队列口径**：工作计划、任务管理、工作台待办对「谁的任务、什么状态、排第几」给出同一答案。
2. **有序执行**：同一实例内的任务按确定顺序串行推进；跨实例可控并发；顺序可人工干预。
3. **执行必回写**：任何一次 Agent 执行结束后，任务项必须得到「结果 + 状态 + 责任人」三件事的更新。
4. **待确认闭环**：执行完成的任务回到实例 owner 手上形成「待确认」，确认后才算闭环；退回则重新排队。
5. **无人值守可预期**：在人类不在岗的时段，队列按配置自动执行；执行前完成工具与权限的准备，执行后以工作日报呈现结果与待确认清单。
6. **自动执行时段可配置、可定时启动**（定时启动本期仅设计）。

## 3. 非目标

1. 不引入「班次 / 批次」这类独立业务对象：任务集合就是队列本身，时段只是队列的执行配置；
2. 不做分布式任务队列、跨机调度与分布式锁；
3. 不做跨工作区编排（任务天然属于单一工作区）；
4. 不允许 Teammate 自主修改任务优先级、责任人、权限或项目归属；
5. 不允许自动扩权：预授权只能「在人类已授权的范围内提前签发」；
6. 不改动工作流任务的审批语义；
7. 本期不实现定时器（只定义规则与契约）。

## 4. 概念与术语

| 术语 | 定义 |
| --- | --- |
| Agent 模版（Profile / Persona） | 定义（SOUL、场景、目标、默认工具白名单），可被多个实例复用；有平台归属概念 |
| Teammate 实例 | 真正承接工作与任务指派的对象；**实例 owner = 该实例的创建人**，与模版归属无关 |
| 任务队列 | 某实例的任务集合视图，按「待启动 → 执行中 → 待确认 → 已完成」组织；即原「工作计划」 |
| 计划项 | 队列中状态为「待处理/待启动」的任务；是常规任务，不是新实体 |
| 自动执行时段 | 队列级配置（可多个时间段，如每天 20:00–08:00）；到点后队列自动按序执行。人不在岗的场景（常说的「夜班」）就是启用该时段的时段 |
| 自动执行轮次 | 系统内部记录：一次「到点开始 → 队列跑空或到点结束」的运行。用于幂等、进度与日报汇总，**不作为产品对象让用户管理** |
| 预扫描（Preflight） | 任务创建后，推断该任务需要哪些工具/资源/审批，并与实例能力对比，得出缺口清单 |
| 预授权 | 人类在进入自动执行时段前，对缺口清单做出的授权决定，落成绑定该任务的 Action Ticket |
| 待确认 | 执行完成、等待实例 owner 验收的任务状态（对应任务状态「待验收」） |
| 反馈项 | 需要人工补充信息才能继续的任务；人工回复即形成新一轮执行指令 |

## 5. 任务队列

### 5.1 队列视图

实例详情「工作计划」页签即工作队列，四个分组：

```text
[待启动（计划项）] → [执行中] → [待确认] → [已完成 / 已归档]
```

| 分组 | 任务状态 | 处理人 | 首屏动作 |
| --- | --- | --- | --- |
| 待启动 | todo | 实例 owner | 调整顺序、预扫描、预授权、取消 |
| 执行中 | progress | 实例（Agent 运行中） | 查看进度、打断、转人工 |
| 待确认 | review | **实例 owner（人类）** | 通过 / 退回并补充 / 转人工 |
| 已完成 | done / cancelled / archived | — | 查看历史 |

### 5.2 口径统一（对既有问题的根治）

三个入口使用**同一套「我的任务」判定**：

```text
归属我 = 责任人是我本人
       ∪ 责任人是「我拥有的实例」（实例 ownerUserId = 我；兼容 teammate id 与员工身份 id 两种形态）
       ∪ 责任人是「我占用的角色席位」
```

要求：

1. 工作台「我的待办」、任务管理「责任人=我」、实例队列三处实现一致，任一修改需同步另外两处；
2. 兼容历史数据：老任务责任人是员工身份 id 时同样命中；
3. 同名实例必须可区分：选择器显示「名称 · 个人/平台 · 实例短码」；
4. 任务管理按实例筛选 = 「该实例承接的全部任务」，与实例队列一致。

### 5.3 排序与并发

排序规则（稳定、可复现）：

1. **人工顺序为准**：用户拖拽/上下移确定的顺序即执行顺序，系统不因优先级变化重排队列；
2. 队列里没有人工顺序时，用「系统 draft 顺序」初始化：优先级 P0 → P1 → P2 → P3 → 截止时间升序（无截止视为最晚）→ 任务 ID 字典序；
3. 新任务入队默认排到**队尾**，不自动插队；若其优先级高于队首任务，只显示「建议优先」提示，由人工决定是否上移；
4. 依赖：前置任务未完成的任务不出队；
5. 优先级只作为**draft 排序与人工判断的辅助信息**，不参与运行时的强制排序。

并发规则：

1. 同一实例同一时刻只执行 1 个任务（串行）；
2. 工作区并发上限默认 2、全局默认 4，与既有进程内队列保持一致；
3. 排队中的任务不因刷新或重启改变相对顺序。

### 5.4 人工干预

| 动作 | 语义 |
| --- | --- |
| 上移 / 下移 / 拖拽 | 调整队列序号，仅影响顺序，不改优先级 |
| 暂停队列 | 停止出队；正在执行的任务不打断 |
| 不参与自动执行 | 单任务标记：自动执行时段内不出队，只等人工触发 |
| 取消 | 任务转 cancelled，从队列移除并留痕 |

## 6. 执行回写与待确认

### 6.1 执行结束必做的三件事

任何一次 run 结束（成功或失败），任务项必须更新：

1. **结果回写**：run 输出摘要写入任务消息（Agent 消息 + runId + 状态），完整产物进产出文档区；
2. **状态流转**：
   - `succeeded` + 开启「自动提交 review」 → 转「待确认（review）」；
   - `succeeded` + 未开启 → 转「已完成」并记录结论；
   - `failed / timeout / cancelled / interrupted` → 留在「执行中」的失败态，附失败原因与重试入口；
   - 需要人工补充信息 → 标记「待补充」，进入反馈项并通知实例 owner；
3. **责任人交回**：转「待确认」时，责任人从 Agent 改为**实例 owner（人类）**，任务动态写明「XX 完成产出物，已提交 YY 确认」。

### 6.2 待确认的处理

| 处理 | 结果 |
| --- | --- |
| 通过 | 转「已完成」，记录验收人/时间，产物归档 |
| 退回并补充 | 追加一条人类指令（必填原因），回到「待启动」（默认队尾），生成新一轮 run；历史全保留 |
| 转人工 | 责任人改为指定人类成员，离开该实例队列 |

**验收人规则**：待确认只认实例 owner。当 owner 离职、停用或不可用时，自动转交**工作区 owner**，并写入审计（这一条同样适用于自动执行结束后的待确认项）。

> 待确认超时的自动处理（提醒 / 转重点关注 / 降优先级）本期不做，留待后续单独设计。

### 6.3 反馈项（需要人工输入才能继续）

Agent 判断信息不足时必须**停在「待补充」**而不是编造结论：

1. 不负责任地标记完成；责任人交回实例 owner；
2. 任务详情顶部给出「需要你补充」的清单（Agent 原文 + 结构化缺口）；
3. owner 回复后，回复内容作为新一轮执行指令，任务重新入队；
4. 自动执行时段内的「待补充」不强推给人类，统一进次日工作日报。

## 7. 自动执行（无人值守时段）

### 7.1 配置

自动执行时段是**队列级配置**，不是独立业务对象。支持两级：

```text
工作区级统一时段（默认模板，可选）
  └─ 实例级配置（可覆盖模板，或单独退出）
自动执行 = 启用开关 + 时段规则（一次性 / 每日 HH:mm / 每周 / 工作日）+ 时区
          + 时长预算（如 10 小时）
```

1. **实例内严格串行**：同一个 Teammate 的任务一个接一个跑；
2. **实例间可并行开始**：同一时段内，多个 Agent 实例各自启动自己的轮次，互不阻塞（受全局/工作区并发上限约束）；
3. 人类在不在岗不影响队列本身，只影响「到点是否自动出队」；
4. 同一实例同一时段同一天只启动一轮（幂等），重复触发忽略；
5. 未配置时段时，队列只能人工触发（现状行为）；
6. 默认值集中在**平台设置**里维护，允许逐级覆盖（见 7.5）。

### 7.2 有序执行

1. 到点后按 5.3 的顺序逐个出队，同一实例严格串行；
2. 单任务超时（默认 30 分钟，可在平台设置调整）→ 标记失败并继续下一个，不阻塞整轮；
3. 失败重试：默认最多 2 次（指数退避），仍失败则标「待确认 · 失败」，本轮继续；
4. 依赖未满足的任务：跳过并留在队列，不报错；
5. 时长预算到点：未开始的任务保持「待启动」且**在下一时段优先执行**（保持队首顺序，不重排、不降级、不标记失败）；
6. 队列顺序在轮次之间保持稳定：上一轮没跑到的任务不会因为新一轮的任务加入而被挤到后面。

### 7.3 无人值守时的动作范围

**允许白名单内的操作**：

```text
可执行 = 实例工具白名单 ∩ 预授权 Action Ticket ∩ 工作区权限
```

1. 只要动作落在上述交集内（含被标记为高风险的动作），自动执行时段**允许执行**；
2. 交集之外的动作一律不做：不降级、不绕过、不猜；
3. 遇到交集之外的需求 → 任务标记「待补充/待授权」并挂起，进次日工作日报，等人类处理；
4. 需要人类实时输入的任务不在自动执行时段内强推。

### 7.4 结果呈现（并入工作日报）

自动执行结束后**不再产出独立的「晨间交接卡」**，结果并入当日工作日报（见运行态交互 PRD 的工作日报模型）：

1. 日报固定包含「无人值守执行小结」章节：完成 N 项 / 失败 M 项 / 待确认 K 项 / 待补充 J 项；
2. 每条结论带任务 ID 与可跳转入口；
3. 需要人类当班处理的事项按优先级与截止时间排序列出；
4. 日报仍是「同一日期一份快照」，可手动更新覆盖（沿用既有规则）。

### 7.5 默认值与配置位置（平台设置模块）

以下参数是**平台级默认值**，在「设置 → AI Teammate 队列」中维护，并允许逐级覆盖：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 单任务执行超时 | 30 分钟 | 超时判失败，继续下一个任务 |
| 队列单轮时长预算 | 10 小时 | 到点停止出队，未开始任务下一时段优先 |
| 自动执行时段模板 | 未配置（关闭） | 工作区级模板，实例可覆盖或退出 |
| 进入自动执行前自动预扫描 | 关闭 | 开启后会消耗模型 token |
| 失败重试次数 | 2 次 | 指数退避 |

覆盖顺序（后者覆盖前者）：

```text
平台设置默认值 → 工作区配置 → 实例配置
```

权限：平台默认值仅平台管理员可改；工作区级由工作区 owner 调整（不得突破平台安全上限，例如超时不得为 0、预算不得超过平台上限）；实例级由实例 owner 调整。

## 8. 预扫描与预授权

### 8.1 目标

让人在进入自动执行时段前就知道：队列里这些任务要动哪些工具、哪些资源、缺什么授权，并一次性完成授权，而不是夜里失败、第二天返工。

### 8.2 预扫描（按需发起，系统默认不做）

**默认不预扫描**：预扫描可能调用模型、消耗 token，属于用户显式发起的动作。

发起方式：

1. 用户在队列里**批量勾选待办任务** → 「发起预扫描」，一次评估多个任务；
2. 单个任务详情里也可以单独发起；
3. 实例配置项「进入自动执行前自动预扫描」默认关闭，开启后才在时段开始前自动扫描（面向愿意承担 token 成本的团队）。

输入：任务标题/描述/验收标准、实例定义（SOUL、场景、目标）、实例工具白名单、工作区与成员权限。

输出（结构化）：

| 字段 | 说明 |
| --- | --- |
| requiredTools | 推断需调用的工具（shell、文件写入、HTTP、检索、子代理等） |
| requiredResources | 资源范围（工作区路径、外部系统、数据域） |
| risks | 敏感动作（删除、外发、生产环境等） |
| gaps | 缺口：白名单未授权 / 资源范围不足 / 需人工审批 / 无可用工具 |
| confidence | 推断置信度与依据 |

要求：

1. 预扫描只做评估，不授权、不执行；
2. **缺少 LLM 或推断失败时，直接按「未知需求」处理**：`confidence=0`、记 `needs_human_approval`，要求人工确认（不猜、不放过）；
3. 结果展示在任务卡徽标、任务详情、自动执行准备清单三处；
4. 任务描述变化 → 结果标记过期并重扫。

### 8.3 预授权（人类离开前完成）

1. 预授权清单来自**用户刚刚勾选并完成预扫描的这批任务**（不是系统自动聚合全队列），按风险分组；
2. 人类逐项决定：允许 / 拒绝 / 缩小范围 / 改为人工处理；
3. 允许即签发绑定该任务的 Action Ticket：`contextType=task`、`contextId=taskId`、`requestedActions`、`resourceScopes`、有效期覆盖该时段；
4. 约束：
   - 不得超出人类自身权限（deny-wins，服务端每次调用复查）；
   - 只对本次时段有效，跨时段需重新确认；
   - 被拒绝的缺口 → 对应任务本轮自动跳过（标记「缺授权」），不空跑；
5. 未发起预扫描的任务按「未知需求」对待：不参与自动执行时段的自动出队（只等人工触发），避免夜里凭空调用工具；
6. 未处理完缺口时仍可到时自动执行，但只跑已授权的任务（默认策略，可在配置里改成「必须全部处理完才自动开始」）。

## 9. 定时启动：由独立调度器承载（仅设计）

自动执行时段的「到点触发」不在 Teammate 模块里实现，而是交给**独立的通用定时器插件 `dsh-collab-scheduler`**（未来还要用于独立的定时任务创建与管理）。

### 9.1 通用调度器的能力（产品口径）

1. **定时任务**：用户可创建/编辑/暂停/删除定时任务，支持一次性、每日、每周、工作日、自定义周期；时区按工作区/组织解释，存储为 UTC；
2. **多种触发目标**：调用 Teammate 执行一轮队列、生成工作日报/晨间简报、启动工作流、发送提醒等；后续可扩展到 HTTP 回调、命令等；
3. **执行历史**：每次触发的开始/结束/结果/跳过原因可查；
4. **手动执行**：任何定时任务都能立即执行一次；
5. **作用域与权限**：个人 / 工作区 / 平台三级归属，按作用域校验管理权限；
6. **幂等**：同一任务同一触发时刻只执行一次；错过窗口按策略处理（补跑 / 顺延 / 跳过）。

### 9.2 与 Teammate 的分工

| 关注点 | 归属 |
| --- | --- |
| 队列顺序、依赖、待确认、反馈项 | Teammate 任务队列 |
| 预扫描、预授权（Action Ticket） | Teammate 任务队列 + 员工插件 |
| 「执行一轮队列」的能力（可手动触发） | Teammate 任务队列（对外只暴露一个入口） |
| 「什么时候执行」 | `dsh-collab-scheduler` |

Teammate 侧只提供「立即开始一轮」的能力，不内置定时器；调度器的第一个触发目标就是它。

### 9.3 启动前检查与错过窗口

1. T-30 分钟检查：实例是否 `active`、队列是否有可执行任务、是否有未决缺口（沿用 8.3 的策略）；
2. 未就绪：默认「按已授权任务启动，其余跳过」；可配置「全部就绪才启动」；
3. 错过窗口：服务在窗口内不可用时，恢复后按剩余时间执行；剩余不足 30 分钟则顺延到下一时段；
4. 手动干预：立即开始一轮 / 暂停 / 终止（终止不影响已完成任务）。

### 9.4 实施顺序建议（含通用性取舍）

**建议：先做队列（含「执行一轮」入口），再做通用调度器；调度器的领域模型可以同期先定。**

理由：

1. 队列（排序、待确认、反馈项、预授权）是产品本体，不依赖调度器就能交付价值；
2. Teammate 侧只需要「执行一轮」这个**可手动触发的动作**，不含任何定时逻辑，因此不会产生后续要删除的临时 timer；
3. 调度器如果先做、没有真实触发目标，容易抽象过度；用 Teammate 自动执行当第一个 target 验证，再接入「独立定时任务」这第二个 target，抽象更稳；
4. 若团队可并行：调度器先落「时间规则 + 触发记录 + target 抽象」的领域模型与最小触发链路，队列同期推进，最后对接。

## 10. 权限与审计

| 场景 | 权限要求 |
| --- | --- |
| 查看队列 | 有权查看该实例及其归属范围 |
| 调整顺序 / 取消任务 | 实例 owner 或平台管理员 |
| 通过 / 退回待确认 | 实例 owner；owner 不可用时工作区 owner 兜底 |
| 配置自动执行时段 | 实例 owner |
| 预授权签发 | 实例 owner，且不得超出自身权限 |
| 手动立即执行一轮 | 实例 owner（平台管理员可代操作） |
| 修改平台默认值（超时 / 预算等） | 平台管理员 |
| 修改工作区级默认值 | 工作区 owner（不得突破平台上限） |

审计要求（追加写入，不可编辑）：

1. 任务出队 / 完成 / 交回 owner / 退回重排 / 转人工；
2. 自动执行时段配置变更、每轮开始与结束、暂停与终止；
3. 预扫描结论与被拒绝的缺口；
4. 每次工具调用对应的 ticket id 与校验结果（失败也留痕）。

## 11. 埋点与成功指标

1. 队列曝光、排序调整次数；
2. 待确认平均处理时长、退回率；
3. 自动执行完成率、失败率、因缺授权被跳过的比例；
4. 预扫描命中率（人工确认的 requiredTools 与实际调用工具的重合度）；
5. 工作日报中「无人值守执行小结」的阅读率与当日事项完成率。

## 12. 验收标准

1. 工作计划、任务管理、工作台待办对同一实例的任务数量与状态一致；
2. 任一 run 结束后，任务必定出现「结果 + 状态 + 责任人」更新，无静默结束；
3. 自动提交 review 的任务，责任人变为实例 owner，并出现在其「待确认」中；owner 不可用时转工作区 owner；
4. 退回后任务回到队列并生成新一轮 run，历史完整保留；
5. 自动执行时段内任务按序串行执行，单点失败不阻塞整轮；
6. 同一时段内多个实例可并行启动各自的轮次，同一实例内严格串行；
7. 人工排序优先于优先级：调整后的顺序在下一轮仍然生效，新任务默认排队尾；
8. 预扫描按需发起（默认不调用模型）：批量勾选任务后 1 分钟内给出缺口清单，无 LLM 时按「未知需求」要求人工确认；
9. 未预扫描 / 未授权的任务不参与自动执行时段的自动出队；
10. 白名单与预授权之外的工具调用被服务端拒绝并留痕；
11. 预算未跑完的任务在下一时段优先执行；
12. 次日工作日报可一次看完无人值守的执行结果与待确认清单。

## 13. 已决策与待确认

已决策（2026-10-12 评审）：

1. 定时触发由独立插件 `dsh-collab-scheduler` 承载，且要按**通用定时任务管理**设计（未来支持用户自建定时任务）；
2. 预扫描默认关闭，由用户批量勾选待办任务后手工发起预扫描 + 预授权；仅在实例配置显式开启时才自动扫描；
3. 允许工作区级统一时段，多实例并行开始；同一实例内严格串行；
4. 人工排序为准，优先级只用于系统 draft 排序与人工判断辅助；新任务排队尾、不插队；
5. 预算未跑完的任务在下一时段优先执行；
6. 验收人只认实例 owner，owner 不可用时转工作区 owner；
7. 自动执行时段内允许白名单 ∩ 预授权范围内的动作（含高风险动作）；
8. 预扫描缺少 LLM 时按「未知需求」要求人工确认；
9. 不产出独立的晨间交接卡，结果并入当日工作日报。
10. 单任务默认超时 30 分钟、队列单轮时长预算 10 小时，均作为**平台设置**中的默认值，允许用户按「平台 → 工作区 → 实例」逐级调整；
11. 待确认超时的自动处理（提醒 / 转重点关注 / 降优先级）**本期不做**，后续单独设计。
