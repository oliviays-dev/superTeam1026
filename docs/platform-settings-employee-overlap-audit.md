# 平台设置：账号与员工模块重叠审计（历史）

> 状态：历史审计与实施记录；Employee 合并目标已被新方案取代  
> 审计日期：2026-10-17  
> 范围：平台设置中的「账号管理」「员工」「角色」，以及与其关联的项目成员、项目角色、AI 伙伴运行时  
> 当前目标方案：`docs/platform-principal-rbac-design.md`

> 2026-10-17 产品方向调整：
>
> 1. 不再建设 Employee 产品域。
> 2. 平台主体改为 Principal。
> 3. 人类使用 Account / Credential。
> 4. AI 使用 AI Principal + AI Companion。
> 5. 未来 HRM 通过 ExternalIdentityLink 对接 Principal。
>
> 本文保留的是重叠问题审计、Phase 0/1 实施记录和早期合并方案。第 4 节之后涉及 Employee 目标模型的描述不再代表当前设计，请以新方案为准。
>
> 后续 Phase 1.5 已撤下企业员工页签，设置入口最终收敛为「账号与权限」；AI 伙伴改为在自有页面创建，并自动绑定隐藏运行身份与关联项目。

## 1. 结论摘要

「账号管理」和「员工」当前存在明确的展示重叠、状态冲突和授权来源冲突，不是单纯的两个页面风格不一致。

当时确认的问题仍然成立：

1. 同一个人同时出现在账号管理和员工目录。
2. 账号状态与员工状态没有同步契约。
3. 工作区授权存在员工域和项目角色两套来源。
4. 数字员工、AI 伙伴、Agent Profile 的状态和生命周期重复。
5. AI 伙伴平台角色曾被错误地从 Owner 派生。
6. Persona、Runtime Profile 和员工目录职责混用。

这些审计结论促成了 Phase 0 的状态修复和 Phase 1 的入口合并。

2026-10-17 后续产品决策进一步调整了目标：

```text
Human Principal ← Account / Credential
AI Principal    ← AI Companion
权限            ← Role Grant(principal, scope)
HRM（未来）      ← ExternalIdentityLink → Principal
```

因此，本文不再建议继续建设 Employee 目录。新的目标信息架构是：

```text
平台设置
└─ 账号与权限
   ├─ 登录账号
   ├─ 角色
   ├─ 授权
   └─ 审计
```

AI 伙伴由左侧「AI 伙伴」管理；当前 Employee 数据仅作为 Principal 迁移前的兼容层。

## 3. 重叠与冲突清单

### P1-1 同一人类出现两个“人员目录”

账号管理列出所有登录账号，员工目录又列出所有登录账号投影出来的人类员工。

表现：

1. 同一个人的姓名同时出现在「账号管理」和「员工」。
2. 两个入口的筛选项、状态、角色和操作不同。
3. 账号管理更像人员目录，员工目录反而只对管理员展示全量。

影响：

- 管理员不知道应该先创建账号还是先创建员工。
- 同一个人可能在两个页面得到不同的状态结论。
- 未来增加 HR 字段后，账号表会继续向员工档案膨胀。

结论：

- 保留一个企业员工目录。
- 账号表降级为员工详情中的“登录凭据”视图或独立账号子页签。
- 创建流程必须保证“先有员工，再可选创建登录账号”，或一次事务内同时创建两者。

### P1-2 账号状态与员工状态没有同步契约

账号状态是 `active / disabled`，员工状态是 `draft / active / suspended / archived`。

当前同步逻辑：

- 员工同步只读取账号的 `id` 和 `name`。
- 员工同步不读取账号状态。
- 账号停用后仍然存在于 `team.users()`，因此员工同步不会把它归档。

证据：

- 账号公开投影只有 `id / name`：`plugins/dsh-collab-employee/src/service.ts:40`
- 同步逻辑：`plugins/dsh-collab-employee/src/service.ts:354`
- 账号停用逻辑：`plugins/dsh-collab-identity/src/index.ts:541`

直接结果：

- 账号已经不能登录，员工目录仍可能显示为「启用」。
- 管理员无法判断这个人是离职、暂停工作，还是仅被安全锁定。
- 后续任务、工作流或通知如果以员工状态为准，可能继续选中一个已无法登录的人。

结论：

- 不能用一个布尔值硬映射成两个业务状态。
- 至少要区分「员工生命周期」和「登录资格」。
- 员工归档或离职必须同时吊销登录；仅安全停用登录时，不一定要把员工归档。

### P1-3 工作区授权存在两套来源

员工域有自己的 `role_assignments`：

```text
employeeId + workspaceId + role(viewer/member/owner) + permissions[]
```

项目与工作流则使用 `dsh-collab-roles` 的席位指派：

```text
workspaceId + seatId + assigneeKind(user/agent) + assigneeId + permissions[]
```

证据：

- 员工授权模型：`plugins/dsh-collab-employee/src/models.ts:62`
- 员工授权写入：`plugins/dsh-collab-employee/src/service.ts:793`
- 项目角色席位：`plugins/dsh-collab-project/src/index.ts:2585`
- AI 伙伴「角色权限」读取员工工作区授权：`plugins/dsh-collab-teammate/client/index.js:2072`

冲突：

1. 同一个 AI 员工可能在「AI 伙伴 → 角色权限」看到一套角色。
2. 在「项目成员」中可能看到另一套项目角色。
3. 工作流派发读取员工工作区授权，项目任务和席位读取角色插件，两套权限解释不同。
4. 员工授权的 `permissions` 是自由字符串，项目角色权限则是固定枚举，无法可靠比较。

影响：

- 同一主体可能在一个入口显示“可审批”，在另一个入口显示“无审批权限”。
- 权限回收可能出现只撤掉其中一套的情况。
- 审计无法稳定回答“这个权限到底来自哪里”。

结论：

- 员工岗位或职级不是安全角色。
- 项目范围的访问权只能保留一套权威来源。
- 推荐项目/工作区范围统一使用项目角色席位和授权表；员工域不再独立创建项目权限。
- 迁移期可以让员工授权 API 变成适配器，转发到统一授权服务，但不能继续双写。

### P1-4 数字员工、AI 伙伴和 Agent Profile 三层重复

当前同一 AI 主体可能同时表现为：

1. AI 伙伴实例：用户日常看到的名称、头像、模版和状态。
2. 数字员工：员工目录中的正式主体、授权和运行身份。
3. Agent Profile / Task Worker：执行引擎中的运行配置。

这是合理的分层，但当前缺少稳定的统一主键和生命周期同步。

表现：

- 员工目录的「数字员工」会显示 `AI伙伴托管` 标签。
- 页面同时提示“数字员工已统一到 AI 伙伴管理”，但员工目录仍保留数字员工列表和详情操作。
- AI 伙伴归档只停用 Runtime Profile，不归档数字员工。
- 数字员工暂停后，AI 伙伴的导入逻辑会映射成 paused，但反向生命周期没有统一事务。

证据：

- 员工目录不再渲染独立数字员工页：`plugins/dsh-collab-employee/client/index.js:3627`
- AI 伙伴归档会停用运行配置：`plugins/dsh-collab-teammate/src/runtime.ts:725`
- 归档记录本身只更新 AI 伙伴状态：`plugins/dsh-collab-teammate/src/service.ts:1119`

影响：

- AI 伙伴显示已归档，员工目录可能仍显示启用。
- 用户无法判断“归档 AI 伙伴”是否等于“员工离职”。
- 同名记录和两个状态入口增加运维与审计成本。

结论：

- 保留三层技术结构，但必须建立唯一员工身份。
- AI 伙伴必须一对一绑定数字员工。
- 面向用户的归档动作应成为一个统一命令，在同一事务或可补偿事务中同步员工、AI 伙伴、Runtime Profile 和登录资格。

### P1-5 AI 伙伴平台角色从 Owner 隐式继承

项目成员展示逻辑会把 AI 伙伴的平台角色派生自 Owner：

`plugins/dsh-collab-project/src/index.ts:769`

风险：

1. Owner 是平台管理员时，AI 伙伴会显示成平台管理员。
2. “创建人”或“负责人”被错误当成安全授权来源。
3. 用户会误以为 AI 伙伴拥有管理员权限，无法判断真实有效权限。
4. 即使当前只是展示派生值，也会污染未来平台角色授权模型。

结论：

- 下线“AI 平台角色继承 Owner”。
- Owner 只表示业务负责人或创建人。
- AI 员工的平台角色必须显式授权，默认不为 `admin`。
- 第一版建议禁止 AI 员工拥有平台管理员角色，只允许显式服务角色或项目范围角色。

### P2-1 姓名存在双写

当前账号表中的 `name` 是登录账号显示名称，员工表中的 `displayName` 是组织显示名称。

当前是单向同步：

- 管理员改账号名称。
- 下次员工列表请求时才同步到人类员工 `displayName`。
- 员工详情本身不允许编辑人类员工的显示名称。

影响：

- 改完账号名称后，员工目录可能短时间仍是旧名称。
- 如果新增邀请、HR 导入或第三方同步，会产生第三条姓名来源。

结论：

- 企业员工档案拥有唯一业务显示名称。
- 账号只保留登录标识、邮箱或认证别名。
- 账号界面显示员工姓名时只读。

### P2-2 “负责人”和“Owner”混用

当前至少有三类归属：

| 字段                         | 实际含义               |
| ---------------------------- | ---------------------- |
| AI 伙伴 `ownerUserId`        | 实例创建人或业务责任人 |
| AI 伙伴 `ownerName`          | 负责人显示名           |
| 数字员工 `managerEmployeeId` | 组织汇报关系           |
| 项目 `ownerId`               | 项目负责人             |

AI 伙伴自动创建数字员工时，`ownerUserId` 会被当作数字员工的 manager。

影响：

- 换工作负责人是否等于换汇报经理，不明确。
- 一个员工离职或转岗时，任务归属和汇报关系可能被一起错误修改。

结论：

- 拆分为 `managerEmployeeId` 和 `accountableOwnerEmployeeId`。
- 汇报关系属于员工档案。
- AI 伙伴使用责任人和运行归属，不应反写组织汇报线。

### P2-3 员工目录的可见性不一致

当前：

- `GET /api/collab/employee` 仅管理员可取全量。
- 普通用户只能退化为查看自己。
- 但员工详情接口允许普通用户查询任意人类员工。
- 员工授权查询接口只要求登录，不校验目标员工和调用者关系。

证据：

- 全量目录管理员限制：`plugins/dsh-collab-employee/src/index.ts:271`
- 普通用户前端退化：`plugins/dsh-collab-employee/client/index.js:1643`
- 授权查询只校验登录：`plugins/dsh-collab-employee/src/index.ts:418`

影响：

- 企业员工目录对普通员工不可用，但项目成员页仍能看到其他 AI 和真人。
- 同一个员工详情是否可见，取决于用户猜不猜得到 URL。
- 授权信息存在被普通登录用户枚举的风险。

结论：

- 明确员工目录可见性策略。
- 建议默认允许查看“启用同事”的有限字段，敏感字段、授权详情和审计仅管理员或 HR/安全角色可见。
- 所有员工详情和授权 API 必须使用同一套对象级权限校验。

### P2-4 平台「角色」页并非平台角色管理

当前 `平台设置 → 角色` 管理的是：

1. Persona。
2. 工作区类型。
3. 工作区席位认领。

它并不管理平台角色，也不管理项目角色定义。

结论：

- Persona 是 AI 行为资产，应移动到 AI 员工配置或 AI 伙伴模版配置。
- 工作区类型和席位属于项目初始化能力，不应占据平台角色主入口。
- 新「角色」页必须管理平台角色定义、权限目录和授权策略。

### P2-5 全局角色值域与工作区角色值域混用

平台角色是 `admin / owner / member / guest`。

工作区成员角色是 `owner / member / guest`。

员工工作区授权又是 `viewer / member / owner`。

同一个 `owner` 在不同层代表不同对象：

- 平台负责人。
- 工作区负责人。
- AI 员工工作区角色。

结论：

- UI 必须始终带范围标签，例如「平台管理员」「项目负责人」「项目角色：Builder」。
- 权限 API 应使用带命名空间的权限 ID，不能只传 `read / write`。
- 项目范围、平台范围、运行限制必须分开计算。

## 4. 目标职责边界

### 4.1 账号 Account

账号只负责认证，不再承担人员目录职责。

保留字段：

- 登录 ID。
- 密码或外部身份绑定。
- 账号状态。
- 最近登录时间。
- 会话。
- 密码更新和重置。
- 安全审计。

新增或明确字段：

- `employeeId`：账号唯一绑定的人类员工。
- `loginStatus`：登录资格。
- `credentialType`：密码、SSO、服务凭据等。

约束：

1. 一个人最多一个主登录账号。
2. 一个账号必须绑定一个人类员工。
3. AI 员工默认没有登录账号。
4. 账号停用不等于员工离职。
5. 员工归档必须使账号登录失效。

### 4.2 企业员工 Employee

企业员工是所有组织身份的唯一目录。

共同字段：

- Employee ID。
- 类型：人类员工或 AI 员工。
- 显示名称。
- 部门、岗位。
- 汇报对象。
- 生命周期。
- 标签。
- 创建、更新时间。

人类员工扩展：

- 登录账号绑定。
- 工作邮箱。
- 入职、离职日期。

AI 员工扩展：

- AI 伙伴绑定。
- Persona 或模版。
- Runtime Profile。
- 工具与资源边界。
- 运行预算。

约束：

1. Employee ID 是任务、工作流、会议、授权和审计的主标识。
2. 人类账号 ID 和 AI 伙伴 ID 都只是员工记录的外部引用。
3. Human Avatar 不进入员工目录。
4. 岗位名称 `title` 不是安全角色。
5. 归档员工不能被新任务、新工作流或新会议派遣。

### 4.3 AI 伙伴 AI Companion

AI 伙伴是 AI 员工在工作区的产品投影，不是第二份员工档案。

保留职责：

- 模版选择。
- 名称、头像和协作说明。
- 当前工作、计划、日报。
- 运行态启停。
- 外部运行时绑定。
- 项目参与和角色权限查看。

约束：

1. 每个 AI 伙伴实例必须绑定唯一 `employeeId`。
2. 每个数字员工最多有一个主 AI 伙伴实例；如需多个实例，必须先定义清楚身份复用策略。
3. AI 伙伴名称最终来自员工档案，实例可保留有限展示别名。
4. 归档 AI 伙伴应同步员工生命周期，或明确降级为“暂停协作入口”。
5. AI 伙伴不直接拥有平台管理员权限。

### 4.4 角色 Role 与授权 Grant

角色定义和授权关系必须分开。

角色定义：

- ID、名称、说明。
- 适用范围：平台、工作区、项目。
- 权限集合。
- 是否系统角色。
- 版本。

授权：

- 被授权员工。
- 角色。
- 范围对象。
- 生效和失效时间。
- 授权人。
- 状态。
- 授权来源。

建议权限目录按范围命名：

```text
platform.user.manage
platform.role.manage
platform.audit.read
workspace.member.manage
workspace.role.manage
project.role.manage
project.audit.read
runtime.ticket.issue
```

迁移期可以先保留现有 `read / write / approve`，但持久化时必须附带 scope，不能只依赖裸字符串。

### 4.5 状态语义

不要再使用一个没有范围说明的「状态」列。

| 状态                 | 含义                   | 主要事实来源    |
| -------------------- | ---------------------- | --------------- |
| 员工生命周期         | 草稿、在职、暂停、归档 | Employee        |
| 登录资格             | 可登录、已停用         | Account         |
| AI 伙伴运行态        | 生效、暂停、失效、归档 | AI Companion    |
| Runtime Profile 状态 | 启用、停用             | Runtime Profile |
| 授权状态             | 有效、已撤销、已到期   | Grant           |

有效能力按以下规则计算：

```text
可登录 =
  员工生命周期为 active
  AND 账号登录资格为 active

AI 可派发 =
  员工生命周期为 active
  AND AI 伙伴运行态为 active
  AND 工作区存在有效角色授权
  AND 存在启用的 Runtime Profile
  AND Runtime Profile 映射可用
```

UI 可以显示一个汇总结果，但必须能展开看到各状态来源。

AI 运行事件与安全事件可以分区，但不要形成无法关联的多条时间线。

## 8. 数据与接口改造建议

### 8.1 不在物理层直接合并 users 和 employees

不建议把账号密码字段直接加到员工表，原因：

1. AI 员工没有密码登录，会产生大量空字段。
2. 账号是认证域，员工是组织域，生命周期不同。
3. 未来接 SSO、服务凭据、外部 Agent 时，认证方式会继续增加。
4. 一张表容易再次把显示名、状态、角色和凭据耦合。

建议保留两个域，但建立明确的一对一映射：

```text
User(authUserId) 1 ── 0..1 Employee(kind=human)
Employee(kind=digital) 1 ── 1 AI Companion
Employee 1 ── N Grant
```

### 8.2 新增统一员工视图

对外提供统一 Employee DTO，聚合：

1. Employee 基础资料。
2. 人类账号摘要。
3. AI 伙伴摘要。
4. 员工项目与授权摘要。
5. 有效状态。

前端不再自行拼接账号、员工和 AI 伙伴三份数据。

### 8.3 统一命令

建议收口以下命令：

```text
createEmployee
updateEmployeeProfile
provisionLogin
resetLogin
disableLogin
suspendEmployee
archiveEmployee
restoreEmployee
assignRole
revokeRole
archiveAiCompanion
```

所有命令同时完成：

1. 业务数据写入。
2. 外部引用同步。
3. 会话或 Runtime 失效。
4. 审计事件写入。

### 8.4 授权兼容策略

第一阶段：

- 员工工作区授权和项目角色席位都保留读取。
- 页面必须标注来源和范围。
- 不允许在同一页面无提示地写入两套。

第二阶段：

- 新写入只进统一授权服务。
- 员工授权 API 作为适配器转发。
- 旧数据做映射和冲突报告。

第三阶段：

- 员工独立工作区授权只读。
- 完成迁移后下线写入接口。
- 历史授权保留审计查询。

## 9. 分阶段落地

### Phase 0：消除状态矛盾

目标：先阻止页面继续给出互相矛盾的结论。

实施状态：已完成 2026-10-17。

1. 账号停用后，在员工目录显示「登录已停用」，不要继续只显示员工启用。
2. 员工归档时自动停用登录账号。
3. AI 伙伴归档时同步员工和 Runtime 状态，或明确改名为「暂停协作」。
4. 去掉 AI 平台角色继承 Owner 的展示。
5. 给账号状态、员工状态和 AI 状态补充同步测试。
6. 员工授权查询增加对象级权限校验。

### Phase 1：合并入口

目标：形成唯一员工目录和唯一账号管理页。

实施状态：已完成 2026-10-17。

1. 新增「身份与权限」设置分区。
2. 企业员工成为默认页。
3. 账号管理改为登录账号子页签。
4. 账号列表增加关联员工和员工详情链接。
5. 新建员工支持人类与 AI 两种类型。
6. 创建人类员工时可选创建账号。
7. 创建 AI 员工时完成 AI 伙伴绑定。
8. 旧入口增加跳转，不立即删除路由。

实施说明：

1. 「身份与权限」是唯一设置导航入口，内部使用 `pluginmax.identity.tab` 子页签。
2. 页签顺序为企业员工、登录账号、角色、审计，企业员工为默认页。
3. 左下角账号按钮与登录失败引导会直接打开「登录账号」页签。
4. 登录账号列表通过 `authUserId` 关联企业员工，并提供“查看员工”跳转。
5. 新增人类员工时可选择同时创建平台登录账号。
6. 新增 AI 员工时选择 AI 伙伴模版、首个工作区和直属负责人，后端一次性创建数字员工、Runtime Profile 与 AI 伙伴绑定。
7. 旧的账号、员工和角色页面组件没有删除，而是迁入统一页签；旧 API 继续保留。

### Phase 2：统一角色与授权

目标：让任何页面看到的有效权限一致。

1. 建立平台角色定义和权限目录。
2. 把 Persona 从角色页移走。
3. 建立统一授权视图。
4. 项目角色写入统一授权服务。
5. 员工工作区授权改为兼容适配。
6. 授权变更统一审计。
7. 增加有效权限解释器，展示权限来源和失效原因。

### Phase 3：清理旧入口

目标：完成兼容期后移除重复界面和写入路径。

1. 下线账号页中的角色和姓名编辑。
2. 下线员工页中独立的数字员工和授权写入入口。
3. 下线员工独立 `role_assignments` 写入。
4. 下线旧「角色」页中的 Persona 和工作区类型。
5. 保留旧路由重定向或只读响应。
6. 数据不物理删除，保留导出和审计。

## 10. 验收标准

### 10.1 身份与展示

1. 同一个员工只在一个企业员工目录中出现一条主记录。
2. 人类员工可以打开关联账号。
3. AI 员工可以打开关联 AI 伙伴。
4. Human Avatar 不出现在员工目录。
5. 修改员工姓名后，账号、项目成员、任务和 AI 伙伴显示一致。
6. 员工目录同时显示员工生命周期、登录状态和 AI 运行态，不用一个模糊状态覆盖三者。

### 10.2 生命周期

1. 员工归档后账号不能登录。
2. 员工归档后不能再被派发任务或工作流。
3. 账号仅安全停用时，员工档案可以保留在职状态。
4. AI 伙伴归档后员工状态和运行态没有矛盾。
5. 归档操作可以追溯到操作者、原因和时间。

### 10.3 角色与权限

1. 平台角色、工作区角色、项目角色在 UI 中始终带范围。
2. 同一个项目权限只存在一个可写事实来源。
3. 回收角色后，任务、工作流和 AI 运行立即按新权限校验。
4. AI 员工不会因为 Owner 是管理员而隐式获得平台管理员权限。
5. 普通用户不能枚举其他员工的授权详情。
6. 授权记录可以回答“谁在什么范围、通过谁、到何时拥有什么权限”。

### 10.4 兼容与审计

1. 旧账号、员工、项目角色和 AI 伙伴数据可以无损迁移。
2. 旧路由在兼容期返回可理解的重定向或只读结果。
3. 登录、员工状态、授权、项目成员和 AI 运行的审计可以按员工关联。
4. 删除或归档不会物理销毁历史任务、工作流、会议和审计。

## 11. 建议优先修复顺序

1. 账号停用与员工目录状态矛盾。
2. 员工工作区授权与项目角色双来源。
3. AI 伙伴归档与数字员工状态不同步。
4. AI 平台角色继承 Owner。
5. 账号和员工双目录及姓名双写。
6. 角色页职责混乱与 Persona 放置错误。
7. 员工目录和授权接口的可见性规则。

## 12. 需要产品确认的四个决策

1. AI 伙伴归档是否等同 AI 员工归档。推荐等同，并在归档确认中明确列出影响。
2. 个人 AI 伙伴是否进入企业员工目录。推荐进入，但标记为个人归属，仅本人和平台管理员可见，支持后续转为企业员工。
3. 普通员工能看到多少同事信息。推荐默认展示启用同事的姓名、部门、岗位，不展示授权和审计详情。
4. 是否允许 AI 员工拥有平台管理员角色。首版推荐禁止，使用项目范围角色或专用服务角色。
