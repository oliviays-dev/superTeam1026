# DSH Pluginmax 工作流产品需求文档（PRD）

## 1. 背景与目标

DSH 的会话负责完成一次具体任务，但跨会话、跨角色的业务推进仍然缺乏稳定骨架：需求评审、开发验收、发布审批、风控处置这类流程经常散落在聊天记录、文档和口头约定里。

工作流能力把“流程定义”和“流程实例”分开：

- 管理员用 Markdown 稳定定义可复用的流程模板；
- 项目成员在中间操作区的“工作流”页签查看当前工作区内的实例状态；
- 会话是过滤视图，不是流程实例的所有者；流程实例始终跟随工作区。

### 产品目标

1. 管理员可以在 10 分钟内读懂并导入一个混合串并行流程。
2. 项目成员进入任意会话后，可以在中间“工作流”页签看到与该会话相关的实例；也可以一键切换到工作区全部实例。
3. 任务、审批、判断、服务节点有明确状态和下一步操作。
4. 审批支持通过、否决、转交、加签。
5. 模板导入时强制检查不可达、未知引用、死循环和缺少 break 条件的循环。
6. 所有用户可读信息优先展示工作区名、会话标题、节点名和人名；不在主界面暴露 UUID。

## 2. 用户与权限

| 角色                     | 能力                                                                                                  |
| ------------------------ | ----------------------------------------------------------------------------------------------------- |
| admin                    | 全局查看；可管理工作区流程定义；可导入、启停、归档模板；可作为审批人。                                |
| workspace owner / member | 可查看所属工作区实例；可在成员会话中启动实例；可完成分配给自己的任务/审批；owner 可管理本工作区模板。 |
| workspace guest          | 只能查看被明确关联且策略允许的实例；不能编辑定义或处理未分配给自己的节点。                            |
| agent                    | 可作为执行者或审批人；只能通过工具/命令读写明确授权的节点；不能管理工作流定义。                       |

权限最终由服务端校验。UI 只做可用性提示，不作为安全边界。

## 3. 核心概念

### 工作流定义

定义是平台共享的版本化模板，由 Markdown 描述。一个 `key` 可以有多个版本；同一时间可以有一个 `active` 版本用于新实例启动，历史版本继续支撑已运行实例。项目在启动实例时提供成员、授权和决策上下文。

定义包含：

- 名称、key、版本、说明；
- 节点：任务、审批、判断、服务、子流程；
- 边：串行、并行汇合、条件分支、默认分支、循环 break；
- 执行者：系统服务、用户、Agent/人设；
- 控制门：指标评分达标、审批通过/否决；
- 可选上下文变量和默认值。

### 工作流实例

实例是定义的一次运行，包含实例标题、工作区、模板版本、节点状态、审批记录、事件、上下文和关联会话。

实例状态：

| 状态      | 含义                                                          |
| --------- | ------------------------------------------------------------- |
| running   | 至少一个节点可执行或执行中。                                  |
| waiting   | 当前节点等待人工/Agent 操作或审批。                           |
| blocked   | 审批否决、缺审批人、循环 break 触发、子流程失败或上下文不足。 |
| completed | 所有汇合终点完成，或到达显式结束节点。                        |
| cancelled | 用户取消。                                                    |
| failed    | 系统/服务节点失败，或子流程失败且父流程未配置兜底。           |

节点状态：

`未触发`、`就绪`、`进行中`、`等待操作`、`阻塞`、`完成`、`跳过`、`失败`。

## 4. 用户场景

### 场景 A：管理员导入流程

管理员进入设置 > 工作流 > 工作区，粘贴或选择 Markdown 文件，点击“校验”。系统显示错误、警告和节点摘要；无错误后可保存。导入页提供图形检查视图，按节点顺序和分支缩进展示流程。

预期：

- 未知节点引用、重复 ID、缺少执行者立即报错；
- 循环没有 break 条件时报错并阻止保存；
- 不可达节点显示警告，允许管理员确认后保存；
- 保存成功后列表出现新版本，并明确显示“草稿 / 启用 / 归档”。

### 场景 B：成员从会话进入流程

成员在左侧选择“后端开发”会话，打开中间“工作流”页签。页面顶部显示“订单中台 / 后端开发 Session”，蓝色过滤标识显示“当前会话相关 · N 条”。

用户可以：

- 切换“当前会话 / 全部工作区”；
- 按状态、关键字筛选；
- 展开流程卡查看节点时间线；
- 对当前节点执行完成、审批、转交、加签或取消。

### 场景 C：串并行混合流程

“支付链路重构”中，技术方案评审通过后，后端改造、前端改造、测试准备并行启动；三者全部完成后进入灰度发布。页签内每个节点独立显示状态，卡片摘要显示最优先需要处理的事项。

### 场景 D：判断节点

复杂度评估节点根据 `complexity >= 8` 进入复杂方案分支，否则走标准开发分支。规则判断自动推进；AI 决策节点必须由授权的 Agent 或用户调用工具/命令给出结论，系统不静默替用户决策。

### 场景 E：审批门

审批节点支持多审批人。默认策略为“全部通过”。用户可以：

- 通过：记录意见与时间；
- 否决：流程转入否决边或阻塞；
- 转交：指定新审批人，原审批人不再必填；
- 加签：在当前审批上追加必签人，已有记录保留。

每次操作写入事件，按钮在提交期间禁用并显示“提交中”。

### 场景 F：受控循环

返工循环允许从“测试失败”回到“开发”。定义必须提供 break 表达式，例如 `attempts >= 3`。运行时每次回到节点会累计 `attempts`；break 条件成立时节点进入阻塞并提示“已触发 break：请修改上下文、取消或联系流程管理员”。

### 场景 G：子流程

“复杂技术方案”节点引用 `complex-review@1`。父实例进入节点时创建子实例并显示引用；子实例完成后父节点完成并继续后续节点。子流程取消/失败时父节点阻塞。

## 5. 信息架构

### 中间“工作流”页签

1. 上下文：工作区名 / 当前会话标题。
2. 标题：项目工作流。
3. 过滤标识：当前会话相关数量或工作区全部数量。
4. 工具行：会话过滤开关、状态筛选、搜索、启动实例。
5. 流程卡：状态点、名称、当前节点、截止时间、状态 pill。
6. 展开区：节点时间线、分支缩进、控制门、待办操作和事件摘要。

### 设置 > 工作流

1. 工作区选择。
2. 定义列表：key、名称、版本、状态、更新时间。
3. 导入/校验编辑器。
4. 图形检查视图。
5. 启动新实例。
6. 归档/启用。

## 6. 交互原则

- 不修改 DSH 主布局；工作流是 `conversation.view` 的一个原生页签。
- 任何提交按钮必须有 pending 态；成功和失败必须有显性反馈。
- 无权限时按钮禁用并说明原因，不允许用户填完才被拒绝。
- 时间统一本地化显示，例如“今天 18:00”“09-12 14:30”；数据库和 API 继续使用 UTC ISO。
- 过滤是视图行为；切换会话不会改变实例所属工作区。
- 空状态区分“未登录 / 无定义 / 当前会话无相关实例 / 工作区暂无实例”。

## 7. 成功指标

1. 导入成功率：首次导入合法模板无需人工修改数据库。
2. 待办发现时间：用户展开页签后 5 秒内能看到自己的待办。
3. 审批操作零歧义：每次通过/否决/转交/加签都有事件和界面反馈。
4. 回归安全：循环无 break、越权操作、跨工作区读取在自动化测试中被拒绝。

## 8. 非目标

首版不做：

- 拖拽式流程画布编辑器；
- 后台定时触发器；
- 自动执行任意 shell；
- 跨工作区流程实例；
- BPMN 完整规范兼容；
- 流程数据迁移到旧 fork。

## 9. 验收口径

- `pnpm check` 通过。
- 管理端可导入、校验、图形查看、启用、归档。
- 中间页签在会话内可用，并能切换会话/工作区过滤。
- 串并行、条件分支、审批、转交、加签、循环 break、子流程均有测试。
- 非成员跨工作区读取、未认证调用、无 break 循环导入均失败。
- GUI 测试方案可按步骤复现 PRD 场景。
