# 项目角色草稿与生效设计（Draft / Confirm）

> 状态：已确认并实现（2026-10-17）。实现细节见第 10 节与项目插件源码。
>
> 本文覆盖「项目级自定义角色」的编辑方式：草稿、覆盖式生效、成员影响确认、
> 工作流模版 / 实例兼容、任务兼容、并发与迁移。

## 1. 已确认的产品规则

1. 「从模版加载」与「复用其他项目」是两个平行入口，同级操作。
2. 取消「应用模版」按钮：选择模版后直接把角色加载到下方列表（草稿），不再单独应用。
3. 列表同时表达「当前已生效的项目角色」与「草稿」。用户可以增删改角色，编辑完成后点「确认」整组生效。
4. 每次确认是**覆盖式生效**，不是增量生效。
5. 若草稿删除了某个角色、且项目成员原本持有该角色，确认时弹窗提示受影响成员；确认删除后，这些成员在该角色上的指派清空。
6. 已经生效的工作流实例不受项目角色编辑影响；新启动的实例使用确认时生效的角色定义。
7. 如果角色变更会使项目已加载的工作流模版失效，该角色不能下线；必须先失效/编辑对应工作流模版。
8. 项目角色名称可编辑；名称不参与上下游匹配，上下游基于角色 code 交互。

## 2. 核心模型

### 2.1 有效集与草稿

- **有效集（effective set）**：`project.projectRoles`，当前对任务派发、工作流启动、成员指派生效的角色清单。
- **草稿（draft）**：客户端编辑中的完整角色清单；只在「确认」时一次性替换有效集。
- 草稿默认只存在当前页面会话（刷新/离开即丢弃），不落库；离开前有未保存提示。
- 有效集带 `rolesRevision`（整数）。每次确认成功 +1；确认请求需要携带 `expectedRevision`，
  防止两个管理员同时编辑互相覆盖。

### 2.2 角色身份

| 字段                                       | 规则                                                                      |
| ------------------------------------------ | ------------------------------------------------------------------------- |
| `code`                                     | 业务身份；项目内唯一、创建后不可修改、匹配模版/其他项目角色时以 code 为准 |
| `name`                                     | 展示名；可编辑；同一项目内不可重名（大小写不敏感）                        |
| `id`                                       | 内部稳定 id；用于底层席位与已存在的任务/工作流引用，不展示给用户          |
| `category` / `description` / `permissions` | 可编辑，不影响上下游引用                                                  |

> 当前底层（`dsh-collab-roles` 席位、任务 `role:`、工作流 `role:`）按 seat id 引用。
> 本设计在项目模块内把 code 作为业务键；是否把底层引用迁移为字面 code，见「待确认决策 3」。

### 2.3 草稿差异（按 code 匹配）

- 有效集与草稿都有的 code：视为「修改」，保留原 role id 与成员指派。
- 只存在于草稿的 code：视为「新增」，生成新 role id。
- 只存在于有效集的 code：视为「移除」，确认后释放该角色的成员指派。
- 名称/分类/权限变化不改变 code，因此不会触发新增/移除。

## 3. 交互设计

### 3.1 入口

入口位于项目详情 →「项目设置」→「项目角色」，与「基础信息」并列为一个设置页签。
成员权限管理只负责增减成员和分配已经生效的项目角色，不承载项目角色定义编辑。

「项目角色清单」标题右侧并列：

`[从模版加载]` `[复用其他项目]` `[添加角色]`

- **从模版加载**：弹窗选择项目模版；选中后直接把模版角色写入草稿（覆盖当前草稿，
  不是覆盖有效集）。若草稿已有改动，先二次确认「放弃当前草稿并加载模版」。
- **复用其他项目**：弹窗选择可访问项目与角色，所选角色合并进草稿（按 code 去重，
  重复的跳过并提示数量）。来源项目不受影响。
- **添加角色**：空白新增，或从角色库预填；code 可自动从名称生成。
- **关闭项目设置**：存在未确认草稿时先弹出放弃确认；选择继续编辑会保留草稿，
  选择放弃则丢弃草稿并关闭整个「项目设置」弹窗。

### 3.2 角色列表

列表始终展示「有效集 + 草稿」的合并视图，行状态：

| 状态                    | 展示                                |
| ----------------------- | ----------------------------------- |
| 已生效                  | 正常行                              |
| 修改（待生效）          | 行标「已修改」，可查看原值/新值     |
| 新增（待生效）          | 行标「新增」                        |
| 待移除                  | 行灰显/删除线，保留「撤销移除」操作 |
| 系统席位（Facilitator） | 只读，不参与草稿，不随确认增删      |

底部操作栏（有草稿改动时出现）：

`新增 X · 修改 Y · 移除 Z` `[取消编辑]` `[确认生效]`

- 取消编辑：丢弃草稿，恢复有效集。
- 确认生效：先服务端校验，再必要时弹「成员影响确认」，最后应用。

### 3.3 编辑角色

- 新增：可填 name / code / category / description / permissions；code 留空时由名称生成。
- 编辑已有角色时先选择保存方式：
  - **调整原有角色**：更新当前角色，code 保持不变（code 只读），成员指派与上下游引用不受影响；
  - **创建新角色**：以当前表单内容另存为新角色，系统生成新的 code
    （`<CODE>_COPY`、`<CODE>_COPY_2`…），原角色与成员指派保持不变；副本以「新增」进入草稿。
- 草稿内尚未生效的新增角色，在确认前仍可调整其 code；已生效角色的 code 不可修改。
- 删除：在草稿中标为「待移除」，不立即删除；确认时才真正下线。
- 角色权限至少选一项；code 为空时由名称生成大写蛇形（如 `SITE_COORDINATOR`）。

## 4. 确认生效流程

### 4.1 客户端确认步骤

1. 前端校验：code 唯一、name 唯一、权限非空。
2. 提交 `confirm`：`{ workspaceId, expectedRevision, roles }`。
3. 服务端返回：
   - `member_impact`：需要二次确认的成员影响 → 弹窗列出「成员 / 将清空的角色」；
     用户确认后带 `ackMemberLoss: true` 重试。
   - `workflow_template_blocked`：角色被已加载工作流模版引用 → 展示阻塞模板与角色，
     不允许确认；提示先失效/编辑对应工作流模版。
   - `revision_conflict`：角色已被其他人更新 → 提示刷新后重试。
     其他错误：保留草稿并提示。
4. 成功：revision +1，有效集更新，草稿清空，席位同步完成。

### 4.2 服务端确认算法（原子）

1. 校验调用者有项目负责人/管理员权限。
2. 校验 `expectedRevision === project.rolesRevision`，否则 409。
3. 校验角色定义（code/name 唯一、权限非空、字段合法）。
4. 计算差异（按 code）：新增、修改、移除。
5. **工作流模版兼容校验**：对项目“已加载的工作流模版”逐个检查角色引用；
   若移除的角色仍被引用 → 409 `workflow_template_blocked`。
6. **成员影响计算**：移除的角色上仍有 active 指派 → 返回 `member_impact`
   （除非请求带 `ackMemberLoss: true`）。
7. **执行**（best-effort 两阶段）：
   - 先物化新席位（按新角色集 + 系统 Facilitator）；
   - 再写 `projectRoles` / `rolesRevision + 1` / `rolesUpdatedAt/By`；
   - 若写项目失败，回滚席位到旧角色集；
   - 若席位物化失败，不写项目记录。
8. 释放被移除角色的成员指派（由 materialize 清理 + 显式 release 兜底）。
9. 返回新的有效集、revision、受影响的成员/角色统计。

### 4.3 成员影响提示

- 只对「确认后将被移除的角色」计算当前 active 指派。
- 弹窗内容：成员姓名/类型 + 角色名称；提示「确认后这些成员在该角色上的项目角色会被清空，
  成员本人仍保留在项目中」。
- 若成员仍持有其他角色，其他角色不受影响。
- 若角色只被 AI Teammate 持有，同样提示；清空后该实例若不再持有任何角色，会从项目成员列表消失。

### 4.4 并发与失败

- 两个管理员同时编辑：后者 confirm 收到 `revision_conflict`，草稿保留，提示刷新后重新编辑。
- 确认期间成员指派被修改：成员影响以服务端确认时的快照为准；若返回影响数量发生变化，前端重新提示。
- 席位物化成功但项目写失败：服务端回滚席位；前端保留草稿。
- 重复点击确认：按钮禁用；服务端用 revision 幂等保护。

## 5. 工作流与任务的兼容规则

### 5.1 工作流模版

- “已加载的工作流模版”口径见待确认决策 2。
- 校验范围：节点 `executor.kind = role` 与 `approvers.kind = role`，两者都按角色 code（经映射）校验。
- 若移除角色会使任一已加载模版出现悬空角色引用 → 该角色不能下线；
  错误里列出「模版名 / 节点名 / 角色名」，并提示先到工作流模版管理失效或编辑模版。
- 修改角色名称不触发该校验；修改 code 不允许；修改权限/分类/说明不触发。
- 新增角色不会使模版失效。

### 5.2 已生效的工作流实例（实例级角色快照）

目标：**已生效实例不受影响，同时角色编辑/删除不被实例阻断**。采用实例级快照：

1. 工作流实例启动时，对定义里引用到的每个角色（执行人 + 审批人）写入
   `roleSnapshot`：`{ roleId, code, name, permissions, members: [{ kind, id }] }`。
2. 该实例后续的角色成员解析、角色标签、角色任务分配全部优先使用快照；
   不再读取项目当前角色集。
3. 项目角色随后改名、改权限、删除角色、清空成员指派，都不影响已启动实例。
4. 新启动的实例按启动时的有效集生成新的快照。
5. 未快照的历史实例（本功能上线前启动的）退回实时解析；上线后新启动的实例才受保护。

安全边界：

- 快照成员仍需满足「当前仍是项目成员」才能操作（人类用户）；从项目移除后不能借旧快照继续操作。
- 快照建立后新加入角色的成员不会进入旧实例（旧实例保持启动时的人员集合）；
  需要新成员参与时请启动新实例或由管理员改派节点。
- 实例快照中的角色名称保持启动时的值；角色改名不会回溯旧实例显示。

### 5.3 新启动的工作流实例

- 启动时按当前有效集校验 `role:` 执行人/审批人；
- 实例内的角色定义取确认时生效的版本（若采用版本快照方案，则实例记录 revision）。

### 5.4 任务（允许删除，标记需改派）

- 已完成 / 已取消任务保留原 `receiverName` 快照，不受影响。
- 角色被删除时，进行中 / 待处理 / 待验收的任务若 `receiverType = role` 且指向该角色：
  - 置为 `receiverState = needs_reassignment`；
  - `receiverType` 改为 `unassigned`，清空 `receiverId / receiverName`；
  - 保留 `previousReceiver`（角色 id/name）与 `reassignmentReason`；
  - 追加一条任务事件「项目角色「X」已下线，任务需改派」；
  - 任务列表显示「需改派」标记，不阻断角色确认。
- 确认响应返回受影响的 `tasksNeedingReassignment` 数量；前端提示「已标记 N 个任务需改派」。
- 若任务标记写入失败：角色确认仍生效，返回 warning；任务列表以「接收角色已不存在」动态兜底显示需改派。

## 6. 边缘 Case 设计清单

### 6.1 草稿与交互

1. 进入编辑即复制有效集为草稿；无改动时确认按钮禁用。
2. 切换项目/页面有未保存草稿：弹窗「放弃草稿 / 继续编辑」。
3. 从模版加载时草稿非空：先确认放弃当前草稿。
4. 复用其他项目时来源项目已被删除/失去权限：确认时服务端校验失败，草稿保留。
5. 复用来源角色 code 与草稿已有角色相同：跳过，并提示跳过数量。
6. 同一角色被移除后又从模版加载同 code：按 code 恢复为「修改」，不重复新增。
7. 新增角色 code 与待移除角色 code 相同：视为恢复该角色，保留原成员指派。
8. 角色名称大小写变化视为修改，不改变 code/席位。
9. 草稿中新增再删除：净变化为零，不触发任何提示。
10. 草稿中删除再撤销：恢复原角色与指派，不触发提示。

### 6.2 校验

11. name 为空 / code 为空 / 权限为空：前端阻止确认并定位字段。
12. code 重复（大小写不敏感）：阻止并提示冲突角色。
13. name 重复（大小写不敏感）：阻止并提示冲突角色。
14. code 在编辑模式被改动：不允许（只读）。
15. 角色数量超过上限（50）：阻止。
16. 草稿为空：允许（等价于清空项目角色），但需要成员影响确认 + 工作流/任务阻塞校验。

### 6.3 成员

17. 被删除角色有真人成员：弹窗列出；确认后清空该角色指派。
18. 被删除角色有 AI Teammate：同上；若实例因此不再持有任何角色，从项目成员列表消失。
19. 成员同时持有其他角色：其他角色保留。
20. 被删除角色无成员：不弹窗。
21. 成员在确认期间被移除/加入：以服务端确认时快照为准，前端提示数量变化。
22. 删除角色后成员列表的角色 chip / 授权范围重新计算。

### 6.4 工作流与任务

23. 角色被已加载工作流模版引用：阻止下线，列出模版/节点。
24. 角色只被未加载的模版引用：允许下线；该模版在项目内不可用（启动校验报错）。
25. 角色被已启动实例引用：不阻断；实例使用启动时快照继续运行（上线前的旧实例除外）。
26. 角色被进行中任务引用：不阻断；任务改为「需改派」，保留原角色快照与原因。
27. 已完成实例/任务：保留历史引用与显示名，不回溯修改。
28. 工作流模版在角色编辑期间被其他人失效/编辑：confirm 时重新校验，按最新状态放行/阻塞。
29. 角色被模版引用但模版处于停用状态：允许下线。
30. 角色 name 修改后：已启动实例显示旧名称还是新名称？建议实例节点使用启动时快照/seatLabel，
    不回溯改名；新实例显示新名称。见决策 1 的快照粒度。

### 6.5 并发与运维

31. revision 冲突：拒绝覆盖，提示刷新。
32. 确认过程中席位服务失败：回滚，草稿保留。
33. 项目角色记录与席位不一致（历史数据/异常中断）：详情页检测并提示“修复角色席位”，
    由管理员触发一次物化对齐。
34. 角色 code 迁移/历史数据：本迭代保持底层 seat id 不变；code 作为不可变业务键，
    创建后不允许修改。若未来改为字面 code 引用，再单独做三插件数据迁移。
35. 审计：记录 `rolesRevision` / `rolesUpdatedAt` / `rolesUpdatedBy`，后续可扩展变更历史。
36. 实例快照成员被移出项目：旧实例保留快照显示，但该用户不再能操作；管理员可改派节点。
37. 旧实例没有 roleSnapshot：按实时角色解析（兼容行为），提示这类实例不受新规则保护。
38. 快照体积：只快照定义中实际引用到的角色，不保存整个项目角色集。
39. 角色删除时同一角色仍有工作流实例在跑：允许；实例快照与成员指派清空并行存在。

## 7. 数据与接口变更

### 7.1 数据

`ProjectRecord` 增加/调整：

- `projectRoles`：项目角色定义（已有）
- `rolesRevision`：整数，默认 1
- `rolesUpdatedAt` / `rolesUpdatedBy`：最近一次角色确认
- （可选）`rolesHistory`：按 revision 保存快照，用于实例回溯；是否落库见决策 1

### 7.2 接口

- `POST /api/collab/projects/roles/confirm`
  `{ workspaceId, expectedRevision, roles, ackMemberLoss? }`
  - 200：`{ project, revision, diff, releasedAssignments }`
  - 409 `revision_conflict`
  - 409 `member_impact`（附 impacts）
  - 409 `workflow_template_blocked`（附 templates）
- `GET /api/collab/projects/role-sources`（已有，供“复用其他项目”）
- 取消/废弃：`/role/save`、`/role/remove`、`/role/import`、`/templates/apply` 的界面入口
  （保留与否见实现阶段；新 UI 只走 confirm）。

## 8. 迁移

1. 现有项目角色视为 revision 1 的有效集。
2. 已有物化席位但无 projectRoles 的项目：按现有迁移逻辑补副本。
3. 角色 id 与 code 的映射保持稳定；name 修改不回写历史实例/任务显示名。
4. 旧界面单条增删接口如保留，仅用于迁移/兼容，不再被新 UI 调用。

## 9. 测试计划

### 9.1 单元 / 路由

- 草稿差异按 code 计算（新增/修改/移除）。
- 覆盖式确认：成员指派保留同 code 角色、移除角色释放指派。
- 成员影响：返回 impacts；ack 后清空对应角色指派；未 ack 不落库。
- 工作流模版阻塞：被引用角色不能移除；停用模版后可通过。
- revision 冲突；重复确认幂等。
- 席位同步失败回滚（fake 注入失败）。
- 角色 code/name 唯一、code 只读。

### 9.2 客户端

- 双入口（从模版加载 / 复用其他项目）与草稿合并。
- 状态标记、取消编辑、确认按钮启用条件。
- 成员影响弹窗、工作流阻塞提示、revision 冲突提示。
- 未保存草稿离开提示。

### 9.3 端到端（GUI）

- 选模版 → 草稿加载 → 编辑/删除 → 确认（含成员提示）→ 生效。
- 复用其他项目 → 合并去重 → 确认。
- 角色被工作流模版引用时删除 → 阻塞提示 → 停用模版后重试成功。
- 两个管理员并发确认 → 后者收到冲突。

## 10. 已确认决策

1. 已生效实例不受影响，且不阻断角色编辑/删除 → **实例级角色快照**（见 5.2）。
2. “加载到项目中的工作流模版” = 项目模版引用的 workflowTemplateIds。
3. `code` 作为不可变业务键；底层继续使用稳定 seat id，不做字面 code 迁移。
4. 角色被进行中任务引用时允许删除，任务标记“需改派”（见 5.4）。

### 备注：为什么不做字面 code 迁移

当前任务、工作流模版、工作流实例和席位里保存的是 seat id（例如 `role-owner`），
而不是展示用的 code（例如 `PROJECT_OWNER`）。改成字面 code 需要把三份插件的历史数据
一起改写，且旧模版/旧实例可能遗漏。本迭代保持 seat id 稳定、code 不可变：
改名不影响任何引用；跨项目/模版匹配按 code；未来若要字面 code 再单独迁移。
