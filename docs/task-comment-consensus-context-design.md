# 任务评论关键共识与 Agent 上下文设计

## 1. 背景

任务详情页同时存在两个信息入口：

- 执行反馈输入框：写入任务执行消息，进入 Agent 上下文，并可能触发 Agent 执行。
- 评论与回复模块：用于协作讨论，支持线程回复，默认不推进任务。

两者不能合并。工作流任务的执行入口由工作流节点控制，评论区仍是工作流任务唯一可用的讨论入口。

本方案解决评论如何影响 Agent 执行，同时避免普通讨论被误当成任务指令。

## 2. 当前实施状态

- 第一阶段已完成：关键共识标签、页面说明、持久化和旧数据兼容。
- 第二阶段已完成：任务 Adapter 输出结构化贡献，上下文模块按上一轮 Receipt 增量注入并记录本轮贡献。
- 记忆沉淀、@ Agent 讨论反馈和共识撤销尚未实现。

## 3. 核心决策

采用两个正交维度：

- `关键共识`：布尔值，由用户显式标记，决定评论是否进入后续真实执行任务的增量上下文。
- `@ Agent`：显式提及，决定是否立即发起一次讨论反馈。

两者不能合并为一个互斥枚举。

| 操作               | 是否立即触发 Agent | 是否进入下次执行上下文     |
| ------------------ | ------------------ | -------------------------- |
| 普通评论           | 否                 | 否                         |
| 关键共识           | 否                 | 是，增量一次               |
| @ Agent 讨论       | 是，发起讨论反馈   | 否                         |
| 关键共识 + @ Agent | 是，立即讨论       | 是，下次执行仍作为共识增量 |
| 普通回复           | 否                 | 否                         |
| 回复中 @ Agent     | 是，讨论反馈       | 否                         |

单条评论默认永远不触发任务执行。只有显式 `@ Agent` 才触发讨论反馈，而且讨论反馈不得改变任务生命周期。

## 4. 产品目标

- 让人类确认过的决策、约束和澄清能够被 Agent 看见。
- 避免所有评论无条件进入上下文，造成噪声和语义污染。
- 避免评论被隐式解释为执行指令。
- 保留工作流任务和普通任务的统一讨论入口。
- 为后续增量同步、@ Agent 讨论反馈和投递审计提供稳定数据基础。

## 5. 非目标

- 第一阶段不把评论注入 Agent 上下文。
- 第一阶段不改变 Agent 触发、任务状态或执行链路。
- 第一阶段不实现 @ Agent 的讨论反馈运行。
- 第一阶段不实现关键共识的修改、撤销和投递游标。

## 6. 用户界面

### 6.1 评论区说明

评论输入区需要明确说明：

> 评论用于协作讨论，不会自动执行任务。勾选“关键共识”仅标记已经确认的决策、约束或结论；本阶段不会因此立即改变任务状态或 Agent 上下文。

### 6.2 关键共识标签

评论输入区增加复选框：

- 标题：`关键共识`
- 默认：未选中
- 辅助说明：`仅标记已确认的决策、约束或结论，不标记个人提议。`

评论列表中的关键共识显示独立标签，颜色与普通状态标签区分。

### 6.3 @ Agent 引导

后续实现 @ Agent 时，提示文案为：

> 将立即通知 Agent 参与本次讨论并回复，但不会被当成本次执行指令。

### 6.4 状态反馈

后续建议显示以下标签：

- `关键共识 · 待下次执行同步`
- `已同步 · 第 N 次执行`
- `已通知 Agent 讨论`

第一阶段只展示 `关键共识` 标签。

## 7. 数据模型

### 7.1 第一阶段

`TaskComment` 增加：

```ts
isKeyConsensus: boolean; // default false
```

该字段只表达用户是否把该条评论标记为关键共识。旧数据读取时默认 `false`。

### 7.2 后续阶段

建议增加：

```ts
consensusVersion: number;
mentions: TaskMention[];
```

并单独记录投递：

```ts
interface SceneContextContribution {
  id: string;
  version?: string;
  text: string;
  sourceRefs: SourceRef[];
}
```

不要通过评论时间推断是否已经投递。每次真实执行应记录已投递的评论版本，保证幂等和可追溯。

## 8. 权限与语义

- 任何任务参与者可以发表评论。
- 关键共识必须代表已确认内容，而不是个人提议。
- 第一阶段允许评论作者在录入时选择是否标记。
- 后续建议限制修改权限：任务创建人、当前人类责任人、具备验收权限的人或管理员可以取消或修改关键共识。
- 关键共识的修改必须保留审计记录。

## 9. Agent 上下文拼装

### 9.1 增量加载

只在真实执行任务时加载关键共识：

- 首次执行：加载当前有效、尚未投递的关键共识。
- 持久会话再次执行、退回重做、追加要求或改派：加载上次执行之后新增或变更的关键共识。
- 无状态 Runtime 再次执行：重新加载当前全部有效关键共识。该 Runtime 不保留上一轮会话状态，只注入增量会让 Agent 丢失仍然生效的决策、约束和结论。
- 普通评论不加载。
- 单纯标记关键共识不触发执行。

执行上下文中应明确说明：

```markdown
## 协作共识增量

以下是人类已确认的任务背景，不是本次新增执行指令。
只有「本次执行要求」决定本轮需要完成什么。

- [决策][2026-10-23 10:46][Admin]
  R9 报告正文控制在 1000 字以内。

- [约束][2026-10-23 10:50][Admin]
  不引用 R9 上市后的销量倒推上市前判断。
```

### 9.2 拼装规则

- 只包含 `isKeyConsensus = true` 的评论。
- 持久会话只包含尚未投递或当前版本发生变化的评论。
- 无状态 Runtime 包含当前全部有效评论，避免上一轮已投递内容在下一轮失忆。
- 保留评论作者、时间和评论 ID。
- 按确认时间正序排列，便于理解决策演进。
- 设置条数和字数上限，超出时由服务端摘要化。
- 不注入完整回复线程，只注入明确标记的评论。
- 不能把关键共识渲染成新增任务要求，必须与执行要求分区。

### 9.3 撤销与替换

- 当关键共识被取消时，下一次执行增加 `[已撤销共识]` 说明。
- 当新共识替代旧共识时，新旧内容都应出现在增量上下文中，并标明替代关系。
- 旧共识不得因为新共识出现而从历史记录中删除。

## 10. @ Agent 讨论反馈

### 10.1 运行类型

@ Agent 使用独立的讨论反馈运行，不复用任务执行语义：

- 不推进任务状态。
- 不修改验收项。
- 不提交交付物。
- 不改写工作流节点。
- Agent 回复写回对应评论线程，不写入执行历史。

### 10.2 上下文

```markdown
## 讨论上下文

本次仅要求你参与讨论并回复观点，不是任务执行要求。

- 发起人：Admin
- 讨论内容：@Agent 这个数据缺口是否会影响结论？
- 讨论性质：未形成项目共识

## 执行边界

不得修改任务状态、验收项、交付物或工作流结果。
如认为该讨论需要转化为执行动作，请明确提出建议，由人类确认。
```

### 10.3 触发规则

- 一条评论可 @ 一个或多个 Agent。
- 同一评论中的多个 Agent 各自收到包含完整任务定义、对应讨论线程和相关文档的上下文。
- 同一线程短时间内的连续 @ 可以合并或排队，避免重复运行。
- `@ Agent` 的运行不消费执行上下文的共识投递游标。

## 11. 增量投递游标

建议在每次运行上下文中保存：

`ContextPack` 与本轮 `ContextReceipt` 记录实际使用的 `contributions`，包含贡献 ID、版本和来源引用。持久会话下一轮通过 `rerunOfRunId` 找到上一轮 Receipt，比较贡献 ID 与版本计算增量，避免重复注入。

无状态 Runtime 没有可复用的会话记忆，因此把已记录的贡献视为“已送达但需重放”，每轮重新提供当前全部有效共识。Receipt 仍记录本轮实际注入内容，便于审计；这里的重复注入是上下文完整性要求，不是评论重复创建或投递循环。

## 12. 分阶段落地

### 第一阶段

本次实现：

- 顶层评论增加 `isKeyConsensus` 标签；线程回复本阶段仍只表示讨论。
- 评论录入区增加复选框和引导说明。
- 评论列表展示 `关键共识` 标签。
- 服务端持久化标签，旧数据兼容。
- 不改变 Agent 执行链路，不注入上下文，不额外触发运行。

### 第二阶段

本次实现：

- 在真实任务执行的上下文构造阶段，增量注入未投递的关键共识。
- 在 `ContextPack` 与 `ContextReceipt` 中记录实际投递的贡献 ID、版本和来源引用。
- 增加执行上下文测试，确认普通评论不进入上下文。

### 第三阶段

- 评论 @ Agent 的讨论反馈运行。
- Agent 回复写回评论线程。
- 增加讨论运行与任务执行的边界测试。

### 第四阶段

- 关键共识修改、撤销、替代和审计。
- UI 显示同步状态与投递历史。
- 处理失败重试、幂等与队列合并。

## 13. 验收标准

- 普通评论不会触发 Agent，也不会进入执行上下文。
- 关键共识在第一阶段只做记录和展示，不改变执行链路。
- 持久会话中的关键共识只随真实执行增量注入一次；无状态 Runtime 每轮重放当前有效共识，避免 Agent 失忆。
- @ Agent 的评论只触发讨论反馈，不改变任务状态。
- Agent 能明确区分关键共识、讨论内容和本次执行要求。
- 工作流任务仍可通过评论讨论，但不会绕过工作流状态控制。
- 旧评论缺少 `isKeyConsensus` 时按 `false` 处理。

## 14. 风险

- 用户可能把个人观点误标为关键共识。需要通过文案、权限和审计控制。
- 关键共识可能过时。需要撤销、替代和版本化机制。
- 评论 @ Agent 可能产生过多运行。需要同线程合并、限流和排队。
- 全量注入会污染上下文。必须坚持筛选、增量、限额和分区表达。
