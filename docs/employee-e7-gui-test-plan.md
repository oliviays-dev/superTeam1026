# E7 Workstation GUI 测试方案

## 准备

1. 仓库根目录执行：
   ```sh
   corepack pnpm install --frozen-lockfile
   corepack pnpm build
   rm -rf .tmp/dsh-home
   ./scripts/install-profile.sh
   DSH_HOME="$PWD/.tmp/dsh-home" node \
     vendor/deepseek-harness/apps/cli/lib/bin.js \
     --profile pluginmax --no-open --port 33117
   ```
2. 使用三个独立浏览器 Profile，不要只用同一浏览器的普通标签页：
   - Profile A：全局管理员，也是工作区 owner；
   - Profile B：工作区 member；
   - Profile C：工作区 viewer 或未加入目标工作区的员工。
3. Profile A 在 Settings >「员工」创建并启用一个 Digital Employee，给它配置当前工作区授权和 Runtime Profile 映射。
4. Profile A 至少导入一个包含审批节点和 `employee:` 执行者节点的工作流模板，并准备一个可启动的实例。
5. Profile A 在会议中派遣一个分身，发送或转发几条消息后退出/关闭会议，确保产生分身报告。

## A1 工作台入口与布局

1. Profile A 登录后打开中间主操作区。
2. 确认 tab 顺序中有「工作台」，点击进入。
3. 检查页面顶部工作区名称、当前会话短标识和工作区切换器。
4. 检查六个面板都出现：员工详情、委托详情、工作流节点、审批、分身报告、管理员权限。
5. 把窗口缩到约 900px 和 390px 宽度。

预期：

1. 工作台不会覆盖左侧栏和会议侧边栏。
2. 面板随宽度换行，文字不重叠，没有横向滚动条。
3. 状态和时间显示中文本地格式；ID 只作为辅助信息。
4. 「按角色面板组合」明确显示“预留”，角色规划不可编辑。

## A2 员工详情面板

1. Profile A 打开「工作台」。
2. 在「员工详情」选择 Profile A 对应的 Human Employee。
3. 再选择已创建的 Digital Employee。
4. 展开工作区授权、Runtime Profile 和审计。
5. Profile B 打开「工作台」，检查「员工详情」可选范围，并展开可见详情。

预期：

1. Profile A 能查看数字员工授权、Runtime Profile、Task Worker 映射和审计。
2. Profile B 默认能看到自己对应 Human Employee 的基础详情；不能看到未授权数字员工的审计。
3. 员工显示名是主标签，Employee ID 只是辅助信息。
4. 所有到期时间不是 UTC 原文。

## A3 委托详情面板

1. Profile A 打开「工作台」>「委托详情」。
2. 选择会议分身产生的委托。
3. 检查主人、上下文、目标、立场、允许动作、禁止动作、发言策略、审批策略和有效期。
4. 点击「延期」，输入 `30`。
5. 点击「暂停」，再点击「恢复」。
6. 点击「召回」。
7. Profile B 打开同一面板。

预期：

1. Profile A 能看到委托完整授权链和对应分身报告。
2. active 委托可延期、暂停、召回；paused 委托可恢复、召回。
3. 每次操作后状态立即刷新并有成功或失败反馈。
4. Profile B 只能看到自己的委托；没有委托时显示空态，不报未捕获异常。

## A4 工作流节点与审批面板

1. Profile A 打开「工作台」>「工作流节点」。
2. 选择目标工作流实例，切换到 `employee:` 执行者节点。
3. 检查执行者显示「员工名 · 数字员工」，责任人显示真人员工名。
4. 节点 ready 时点击「派发」，等待运行状态变化。
5. 切换到审批节点。
6. 用不是审批人的 Profile B 查看该审批。
7. 用审批人 Profile 打开「工作台」>「审批」，填写意见，先点击「否决」或「通过」。
8. 回到「工作流」tab 或刷新工作台，检查实例状态。

预期：

1. 节点状态、尝试次数、说明、运行记录和节点事件可读。
2. 派发、完成和刷新操作只调用工作流服务端 API；无权限时显示服务端错误。
3. 不是审批人时不能点击通过/否决；数字员工审批明确显示等待专用 runtime decision path。
4. 审批操作后审批记录显示已通过/已否决、时间和操作人；下游节点按定义推进。

## A5 分身报告面板

1. Profile A 打开「工作台」>「分身报告」。
2. 用分身名、主人名和报告内容分别搜索。
3. 展开成功报告。
4. 若存在失败报告，展开失败报告。
5. Profile B 重复搜索自己的分身报告。

预期：

1. 报告按委托名和主人可读展示，不以 delegation UUID 作为主标签。
2. 成功报告能看到固定结构内容；失败报告显示原因，不伪造成功。
3. Profile B 只能看到自己拥有的分身报告。

## A6 管理员权限面板

1. Profile A 打开「工作台」>「管理员权限」。
2. 检查员工数、授权数、Runtime Profile 数和有效票据数。
3. 展开授权矩阵，检查员工名、工作区名、角色、权限和到期时间。
4. Profile B 和 Profile C 打开同一面板。

预期：

1. 只有全局管理员能看到治理汇总和授权矩阵。
2. 非全局管理员看到明确的权限提示，不出现空白或未捕获异常。
3. 数字员工权限必须能对应到显式工作区授权，不显示来自 Persona 的权限来源。

## A7 预留面板组合

1. Profile A 检查「按角色面板组合」。
2. 尝试寻找编辑、拖拽、保存布局入口。
3. 对比页面的 admin/owner/member/viewer 规划和当前固定面板。

预期：

1. 页面明确显示预留 schema，不提供保存或启用按钮。
2. 当前六个基础面板仍按固定布局可用。
3. 用户不会误认为角色定制布局已经生效。

## 通过标准

1. Workstation 只组合现有服务端能力，没有新增绕过权限的本地数据通道。
2. 六个基础面板都能加载、筛选、展示和执行各自允许的操作。
3. 预留的 by-role 面板组合可见但不可用，边界清晰。
4. 浏览器 Console 没有未捕获异常。
