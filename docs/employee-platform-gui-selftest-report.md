- 日期：2026-09-19
- 测试对象：`employee platform` / E0-E7 当前实现
- 测试方式：浏览器人工自测 + 控制台检查；本报告不覆盖产品代码
- 参考方案：`docs/employee-platform-gui-test-plan.md`
- 隔离环境：`.tmp/gui-test-home`，`http://127.0.0.1:33118/`
- 测试工作区：`gui-test-workspace`
- 测试账号：`workflow-owner / workflow-member / workflow-viewer`

## 1. 结论

当前平台方向性可用：Human Employee、Digital Employee、Human Avatar / Delegation、显式授权、治理中心、分身报告、工作台集成等主链路已经能走通。员工目录与委托数据边界基本正确，数字员工没有进入真人员工目录；会议派遣生成的委托能够生成报告，并且暂停 / 恢复、治理中心与工作台之间可以互相追溯。

但当前版本不建议进入发布状态。主要原因是审批完整性仍有两个 P0 缺陷：未来审批节点可能提前审批，以及一个真人否决用例在 GUI 和存储数据中均保持不变且没有错误反馈。此外，工作流主列表与工作台节点面板还存在数据一致性缺陷，部分运行记录会把主体名渲染成 `undefined`。

自动化门禁已通过：typecheck、lint、unit、build、contract、pack check 均通过；unit 为 94 passed。GUI 自测未发现未捕获异常，但刷新时出现过一次连接重连 warning，不作为阻塞项。

## 3. 已验证的关键行为

1. `Workflow Owner` 以全局 `admin` 登录后，工作台能看到员工详情、委托详情、工作流节点、审批、分身报告和管理员权限面板。
2. `Workflow Member` 登录后，管理员权限面板不显示治理明细，只显示「此面板需要全局管理员权限」；员工详情仍按当前用户显示。
3. 员工详情能区分「真人员工」和「数字员工」。
4. `Backend Engineer 01` 显示独立的工作区授权和 Runtime Profile：`backend-runtime · gui-test-workspace · spawn/默认模型 · Task Worker backend-agent`。
5. Human Avatar 委托显示 `Human Avatar`、主人、上下文、目标、授权 / 禁止、发言 / 审批边界；未混入员工目录。
6. 分身报告在委托详情、分身报告面板和治理报告中均可展开，报告内容包含会议关键过程、立场、结论、风险、待主人确认、后续建议和信息缺口。
7. 工作台分身报告搜索能命中报告关键词；不存在的关键词显示「没有匹配的分身报告」。
8. 非审批人界面保持只读，显示等待对应审批人操作；数字员工审批节点显示等待专用 runtime decision path，不提供真人代签按钮。
9. by-role 面板组合区显示 `预留 · schema v1`、ADMIN / OWNER / MEMBER / VIEWER 规划模块，并明确角色定制编排尚未启用；未发现编辑、拖拽、保存入口。
10. 工作流节点事件时间在当前 UI 中多数显示为本地可读时间，例如 `2026/09/19 16:55`。

## 4. 缺陷清单

### P0：发布阻塞

#### P0-1 未来审批节点可以被提前审批

- 现象：审批节点尚未成为 active / ready 状态时，界面或公开 API 仍允许完成审批。
- 影响：流程门禁可被绕过，审批时间和流程状态不可信。
- 期望：只有节点进入待审批状态后才接受 approve / reject；其他状态必须返回明确错误。
- 回归：创建多节点实例，在未来审批节点仍为 waiting 时调用 GUI 或 API，确认被拒绝且不产生审批记录。

#### P0-2 真人否决静默失败

- 现象：`workflow-member` 对 F8.4 用例填写否决理由并点击「否决」，界面状态和数据存储均保持不变，且没有错误提示。
- 影响：用户以为已经否决，但流程仍停在等待状态；审批操作不可追溯。
- 期望：服务端成功后更新否决状态、否决原因、操作人和时间；失败时 UI 显示可读错误并保留已填写内容。
- 回归：新建待审批实例，输入 `交付说明缺少风险项。`，点击否决后刷新，确认节点、实例、事件、审计均出现否决结果。

### P1：主要功能正确性

#### P1-1 F8 实例不在主工作流列表中稳定出现

- 现象：`F8 数字员工审批等待` 在存储和工作台节点选择器中存在，但刷新后主工作流列表没有稳定显示。
- 影响：管理员无法从主流程入口追到该实例。
- 期望：同一工作区、同一权限主体下，工作流主列表与工作台节点选择器返回一致的运行实例集合。

#### P1-2 Task Worker 运行记录主体显示 `undefined`

- 现象：`Employee 节点回归` 的运行记录显示 `Task Worker · 失败 · undefined`。
- 影响：失败无法定位到具体 Profile 或员工。
- 期望：过渡 Task Worker 至少显示 profileId；Digital Employee 显示员工名 / employeeId；缺失主体时显示明确空状态或错误。

#### P1-3 真人员工详情缺少工作区授权管理入口

- 现象：真人员工详情能看到授权记录，但管理员没有对应的授权管理操作区。
- 影响：F4 的授权创建 / 更新 / 撤销在真实员工详情上不闭环。
- 期望：管理员可以在员工详情中管理指定工作区的显式授权，并看到结果反馈和审计。

#### P1-4 员工选择器与详情数据不一致

- 现象：Profile B 工作台员工选择器显示 `Workflow Member`，但详情字段短暂或持续显示 `Workflow Owner`。
- 影响：用户可能误操作另一个主体的数据。
- 期望：选择器变更后立即重取并渲染当前 employeeId 的详情；显示名、主体类型、授权、审计全部同步。

#### P1-5 Digital Employee 审批模板导入校验不一致

- 现象：同一类审批定义先因 task-worker 规则被拒绝，补充 approve 权限后又要求显式权限，路径不一致。
- 影响：用户无法判断正确模板写法。
- 期望：导入前一次性完成 employee approver、权限和 Runtime 映射校验，并返回包含字段名的完整错误。

#### P1-6 Digital Employee 审批等待态错误出现「派发」入口

- 现象：审批等待节点不是任务执行态，但节点面板仍显示「派发」。
- 影响：用户可能把审批节点误当任务节点派发。
- 期望：approval 类型节点只显示审批状态与 runtime decision path，不显示任务派发按钮。

#### P1-7 暂停 Digital Employee 后节点 UI 状态错误

- 现象：暂停数字员工后，部分节点仍出现可派发或可完成的状态。
- 影响：暂停边界不能稳定阻断操作。
- 期望：paused / archived 员工所有新派发禁用；进行中节点显示明确阻塞原因。

#### P1-8 运行尝试次数与节点尝试次数口径不一致

- 现象：工作流 run attempts 与 node attempts 在重派后显示不同数值。
- 影响：审计和失败分析无法判断实际第几次执行。
- 期望：统一显示「节点第 N 次尝试」和「本 run 内第 N 次尝试」，事件记录使用同一序号。

#### P1-9 缺失 Runtime 校验过早或过晚不一致

- 现象：某些模板在导入时即因缺失 Runtime 被拒绝，而另一些直到派发才失败。
- 影响：定义者无法在导入阶段获得稳定反馈。
- 期望：导入时校验引用的 employeeId / profileId 是否存在；运行时如映射失效，返回明确阻塞而不是继续排队。

#### P1-10 治理搜索对中文关键词和主体关联不完整

- 现象：`失败`、`审批`、`报告` 等中文关键词没有命中预期记录；`backend-01` 也没有稳定召回关联活动。
- 影响：治理中心难以用于事故追溯。
- 期望：搜索覆盖结构化字段、事件消息、审批意见、报告正文、employeeId 和相关 run / ticket。

### P2：体验与可读性

#### P2-1 部分审计 / 表格仍显示原始 ISO 时间

- 现象：协作身份的审计时间线等表格仍显示 `2026-09-19T07:38:46.573Z`。
- 影响：和会议、工作台已本地化的时间显示不一致。
- 期望：统一显示 `YYYY/MM/DD HH:mm`，悬停保留完整 UTC 信息。

#### P2-2 长时间标识和复制能力不完全一致

- 现象：部分详情已缩短显示，但不是所有 employeeId、workspaceId、runId、ticketId 都有 hover / copy。
- 影响：跨页面追溯时需要从外部复制。
- 期望：所有主体 / 上下文 / 运行 ID 使用短标识 + hover 完整值 + copy。

## 6. 环境限制

1. Avatar / Delegation 的自然到期边界无法在不修改系统时间的情况下完整验证；本次只验证 active、paused、completed 状态。
2. 900px 与 390px 视口检查受浏览器工具限制未执行，后续可在 Chrome DevTools 或 Playwright 项目中补充。
3. F8.4 的否决缺陷已通过界面和存储状态复现，但为避免污染更多下游用例，未继续在该实例上做破坏性重试。
4. 本轮自测不修改产品源码，只新增测试夹具和测试数据。

## 7. 建议修复顺序

1. 先修 P0-1 和 P0-2，建立统一的审批状态机防护：`waiting` 节点不可审批、active 才可审批、approve / reject 必须持久化、失败必须显式返回。
2. 修 P1-1 和 P1-2，保证主工作流列表、工作台节点、运行记录使用同一查询和同一主体名格式。
3. 修 P1-4 到 P1-9，收敛导入校验、员工状态、派发状态和尝试次数口径。
4. 补齐真人员工授权管理 UI 与数字员工审计可见性。
5. 最后处理 P2 的时间 / ID 可读性和治理搜索。

## 8. 最小回归集

修复后建议优先执行以下用例：

1. 审批状态机回归：waiting / active / passed / rejected / blocked 五种状态下 approve 和 reject 的 UI 与 API 结果。
2. 真人否决 E2E：否决后实例不完成、下游不 ready、事件和审计有记录、刷新后状态不变。
3. 非审批人边界：Profile A / C 均无操作入口，直接 API 调用被拒绝并留审计。
4. 数字员工审批：无真人代签按钮，等待专用 runtime decision path，禁止手动派发。
5. Task Worker 失败追溯：运行记录显示 profileId 或 Digital Employee，事件包含 runId、ticketId 和节点尝试序号。
6. 暂停 / 归档员工：新派发禁用，进行中节点阻塞原因明确，治理风险出现对应条目。
7. 主列表一致性：同一工作区刷新后，主工作流列表、工作台节点选择器和治理中心实例集合一致。
8. 员工详情一致性：切换 employee 后，详情、授权、审计和操作按钮全部跟随当前 employeeId。
9. 治理搜索：`backend-01`、`失败`、`审批`、`报告` 均能命中对应记录。
10. 响应式复查：1280px / 900px / 390px 下工作台六面板、工作流启动表单和员工 Runtime 表单无遮挡、无双滚动条。
